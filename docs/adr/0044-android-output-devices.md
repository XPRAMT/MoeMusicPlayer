# Android output device choice

Status: Accepted (built and unit-tested; the device list was seen on a phone, the rest not yet verified on a device)

Decision date: 2026-10-27, Asia/Taipei (UTC+08:00)

## Context

Windows has a playback device list in Settings → 播放 (ADR 0020). On Android the player always followed the system's routing: plugging in a USB DAC or connecting a headset moved the sound, and there was no way to keep playing on the phone speaker while a headset is connected, to prefer a USB DAC over Bluetooth, or to see what the output really is. The user asked for the Android equivalent of the Windows list, with the same look, limited to what Android can do.

Android facts that shape the design:

- `AudioManager.getDevices(GET_DEVICES_OUTPUTS)` lists the attached outputs without any permission; `AudioDeviceCallback` reports every change (and is called at once with every attached device on registration).
- `AudioDeviceInfo.getId()` changes every time a device is plugged in, so it cannot identify a device across plugs or restarts. Type, product name and (for Bluetooth) address are stable.
- Media3 `ExoPlayer.setPreferredAudioDevice(AudioDeviceInfo?)` pins the AudioTrack to a device (`AudioTrack.setPreferredDevice`); null returns to the system's routing. A preferred device that goes away makes the platform route to its default.
- Capabilities per device: `getSampleRates()`, `getChannelCounts()`, `getEncodings()`; an empty array means "any" (the platform converts).
- What really plays: Media3's `AnalyticsListener.onAudioTrackInitialized` gives the `AudioSink.AudioTrackConfig` (encoding, sample rate, channel mask, offload); the routed device is `AudioTrack.getRoutedDevice()`, which Media3 does not expose, so the default `AudioTrackAudioOutputProvider` is wrapped (`RouteObservingOutputProvider`) to see each AudioTrack it creates. On Android 13+ `AudioManager.getAudioDevicesForAttributes(media)` says where the system sends media when no track is open.
- Everything still goes through the Android mixer (AudioFlinger), which may resample, and a Bluetooth headset gets whatever its codec carries: the AudioTrack format is what the player hands to Android, not what the device receives. On the phone a WF-1000XM6 over LDAC showed an AudioTrack of 44.1 kHz float and a declared device format of 48 kHz 16-bit while the codec streamed 96 kHz 32-bit, so the playing row shows each step with whose rate it is (the mixer, the codec), and the declared format is only on rows that are not playing.
- The current Bluetooth codec: `BluetoothA2dp.getCodecStatus` is a system API (not in the public SDK, not even at API 37), and hidden APIs are not used. `BluetoothCodecStatus` / `BluetoothCodecConfig` are public since Android 13, and the Bluetooth stack sends the codec status in a broadcast (`android.bluetooth.a2dp.profile.action.CODEC_CONFIG_CHANGED`, extra `BluetoothCodecStatus.EXTRA_CODEC_STATUS`) to holders of BLUETOOTH_CONNECT on connection and on every codec change. That broadcast is the only legal source; it is not sticky, so a headset that was connected before the process started is unknown until it reconnects or its codec changes.

## Decision

- **One choice, single selection**: 「系統預設」 or one device, stored in `settings.json` as `androidOutputDevice: { kind, productName, address? } | null` (Rust `settings::AndroidOutputDevice`, serde default null; an unreadable value loads as null). Both defaults (Rust and the page) are the system default.
- **Identity** (Kotlin `AudioOutputRules`, the only place the rule lives): `kind` groups `AudioDeviceInfo` types — `speaker`, `wired` (headset and headphones: one jack reports either), `usb` (device, accessory, headset: one DAC can report either), `bluetooth` (A2DP), `bleAudio` (LE Audio headset/speaker), `hearingAid`, `hdmi` (HDMI, ARC, eARC), `line` (analog, digital, aux), `dock`. Earpiece, telephony, SCO, the alarm "safe" speaker, buses, remote submix, FM, IP and the BLE broadcast are not listed. Identity = kind + trimmed product name, plus the address for the Bluetooth kinds; an empty address on either side does not count against a match, and an address Android hid (`XX:XX:XX:XX:AB:CD`, without BLUETOOTH_CONNECT) matches by its last two bytes. A device the platform reports twice under one identity is one row whose capability lists are the union. The page stores the `identity` object Kotlin sends with each device, so the page has no copy of the rule; the status command passes the saved choice to Kotlin, which answers with the matching `chosenId`.
- **Applied by the service, not the page**: the Rust process keeps the choice (`android_output::set_preference`, set at startup from the settings and on every change) and `PlaybackService` reads it over JNI (`nativeOutputDevicePreference`) when it is created and before every load, so the choice applies with no Activity or WebView. A change on the settings page is also pushed to a running service (`setAudioOutputPreference`). `AudioOutputRouter` registers an `AudioDeviceCallback` and on every device change pins the player to the chosen device if it is attached, else to the system default; when the device is plugged back in it is pinned again automatically. It calls `setPreferredAudioDevice` only when the target changes.
- **What the page shows** (`AndroidOutputDevicesSettings.svelte`, `android-output-devices.js`; the row classes are shared with the Windows list, and every format line comes from the one formatter `src/lib/output-format.js` that the Windows list uses, ADR 0020 "Output path line and supported rates"): 「系統預設」 first (`目前是：{device}` like Windows), then the listed devices. A row that is not playing lists what `AudioDeviceInfo` declares in the Windows idle format, every rate then the channels, no bit depth (`describeSupport` → `formatSupportedFormats`): `44.1, 48, 96 kHz．2 聲道` (格式不限 when nothing is declared, or 由藍牙編碼決定 for a Bluetooth, LE Audio or hearing-aid device, whose format the negotiated codec sets; 取樣率不限／聲道數不限 for a missing half). The row that plays (the chosen device, or 「系統預設」 when nothing is chosen) has instead the path line in the Windows format (`describeAndroidPath`): AudioTrack rate → mixer rate（系統） → codec rate（codec）．N 聲道, e.g. `96 kHz → 96 kHz（系統） → 96 kHz（LDAC 最佳效果）．2 聲道` (G8142), `96 kHz → 48 kHz（系統） → 96 kHz（LDAC）．2 聲道` (RedMagic and the tablet, codecSpecific1 0 gives no quality), `48 kHz → 48 kHz（系統）．2 聲道`. Rules: the 系統 step is shown whenever the mixer rate is known, also at the AudioTrack's own rate; an unreadable mixer rate leaves the step out (`96 kHz → 96 kHz（LDAC 最佳效果）．2 聲道`), never a guessed number; a Bluetooth route always ends with the codec step, even at the same rate, because it names the codec (LDAC adds its quality: the bitrate of the setting, 990/660/330 kbps in the 48 kHz family and 909/606/303 in the 44.1 kHz family, or 最佳效果 for the adaptive one; just the codec name when neither is known), and before the stack has reported the codec, or without the permission, the step is 「（藍牙）」 with no rate; an offloaded track adds 「．硬體解碼」. The mixer rate is `AudioTrack.getNativeOutputSampleRate(STREAM_MUSIC)` (public API; it follows the stream's current route), read by `AudioOutputRouter` when the AudioTrack is initialized and on every routing change, and sent as `output.mixerSampleRate` (null when it fails or is 0; Kotlin `AudioOutputRules.mixerRateOf`). The path is what Android is handed and what the mixer and codec run at, not a claim about what the device receives, and never bit-perfect. The chosen row shows the path whenever an AudioTrack is open; without a routing report it is the chosen device's own path (its codec step included), because the player is pinned there. A chosen device that plays elsewhere (the routed device is another identity; the same device under another id does not count) shows `目前由 {0} 播放：{path}` as a warning. The open AudioTrack's format is kept by `LiveTrackOutput`, which counts `onAudioTrackReleased` against `onAudioTrackInitialized`: Media3 can report the old track's release after the new track opened (re-pinning while playing), and clearing on that late release made the playing row look idle (2026-10-28, NX809J with a Bluetooth headset; logcat tag `MoeMediaIndex` logs each track's initialisation and release). A chosen device that is not attached stays as a row with 「已中斷連線，目前改由 {0} 播放」 naming the device actually used (the routed device, else the system's media route on Android 13+; without either it says 「已中斷連線」). The list is re-read every 2 s while it is shown (the service itself reacts to the callback at once). The settings page and the quick-settings drawer share one module state (src/lib/AGENTS.md rule); only the permission panel belongs to the copy whose button was pressed.
- **Not on Android**: shared/exclusive, presets, volume link, per-device volume and delay, channel map, several devices at once, DSEE HX.
- **Permissions**: BLUETOOTH_CONNECT (「附近的裝置」, Android 12+) for the codec broadcast and the full Bluetooth names and addresses, following ADR 0039: declared in the plugin manifest, never asked at startup; without it a Bluetooth row on Android 13+ says 「需要『附近的裝置』權限才能讀取藍牙編碼」 with 「前往授權」, which opens the explanation panel, and only the panel's 「前往授權」 requests it (a refused prompt that no longer shows opens the app's settings page). Before Android 13 there is no codec to read, so nothing is asked and the line is absent; before Android 12 the permission does not exist. `getDevices` needs no permission. A choice saved while Android hid the address (`XX:XX:XX:XX:AB:CD`) still matches the full address once the permission is granted, and the other way round, by the last two bytes; an empty address on either side does not count against a match; a name the system hides shows as the kind (藍牙).
- No code was taken from other players; EchoTide-Music (AGPL) was not used as a source.

## Consequences

- A chosen USB DAC keeps the player on it while Bluetooth connects and disconnects; unplugging it falls back to the system's choice and plugging it back re-pins, with no user action.
- The AudioTrack provider is the default one built by `AudioTrackAudioOutputProvider.Builder(context)` (what `DefaultAudioSink.Builder` builds when none is given), wrapped only to observe tracks. `DefaultAudioSink.getAudioCapabilities()` returns null with a provider that is not the default class; Media3 uses it only for IAMF output, which the player does not play.
- Unit tests: Kotlin `AudioOutputRulesTest` (filtering, dedup, identity, re-plug matching, Bluetooth address rule incl. hidden addresses, preference parsing) and `BluetoothCodecRulesTest` (codec names, rate/bits/channel flags, LDAC bitrates), Kotlin `mixerRateOf`; JS `tests/android-output-devices.test.mjs` (labels, the idle line, permission flow, rows incl. the disconnected row) and `tests/output-format.test.mjs` (the shared path line of both platforms incl. the mixer step at the same rate, an unknown mixer rate, a codec not reported yet and codec step names), Rust settings and `android_output` tests.
- Future work, not done: direct/bit-perfect output (`AudioManager.setPreferredMixerAttributes` on Android 14+ for USB, `AudioTrack` direct playback), USB exclusive access, per-device volume.
- Needs device verification: pinning and re-pinning with a real USB DAC and Bluetooth headset, the routed-device display and the path line (that `getNativeOutputSampleRate` reports the routed output's mixer rate on each device), the codec broadcast (that it arrives with the permission and the receiver flags used, and the values for LDAC/AAC/SBC), Bluetooth names and addresses with and without BLUETOOTH_CONNECT, the permission panel and the settings-page fallback, the system route on Android 13+ vs older devices, and that wrapping the AudioTrack provider changes nothing else in playback.
