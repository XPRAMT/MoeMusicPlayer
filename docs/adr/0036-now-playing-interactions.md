# 播放頁互動：封面縮放、手勢、睡眠定時與播放鍵狀態

Status: 已採納

## Context

播放頁的封面縮放、觸控／滑鼠手勢、睡眠定時與 seek 期間播放鍵的行為原本只記在 AGENTS.md，沒有對應的 ADR。此 ADR 記錄其目前設計。

## 目前設計

播放鍵與 seek 期間：`PlaybackService.kt` 的 `playbackStateName` 在 `playWhenReady && STATE_BUFFERING && 有項目` 時回 `"buffering"`（快照節流看 `playWhenReady`）；Rust `android_playback.rs` 的 `counts_as_playing`（playing／buffering）決定 `is_playing`、`resumePlayback` 與換曲 `play_when_ready`，收聽計時只算 `"playing"`；前端 `PlaybackState` 有 `buffering`，播放時鐘與現場播放次數只在 `playing` 前進。seek 走 `sendPlaybackCommand(..., { seek: true })`（設 `isSeeking`）；點擊處理在 `isSendingPlaybackCommand || isSeeking` 時忽略但外觀不變（從清單選曲例外：不看忙碌旗標、最新選擇勝出，見 `playback-command-order.js`）；上一首／下一首 `disabled` 只看 `playbackNavigationReady` 與有無上／下一首；播放、隨機、循環在其他指令忙碌時 disabled。測試：`tests/seek-transport-lock.test.mjs`、`PlaybackProtocolStateTest.aSeekWhilePlayingIsBufferingNotAPause`（`src-tauri/gen/android` 下 `gradlew :tauri-plugin-media-index:testDebugUnitTest`）、`android_playback::integration_tests::a_seek_buffering_snapshot_keeps_playing_without_flipping_resume_or_counting_time`。

正在播放封面縮放（`src/lib/cover-zoom.js`，action `coverZoom` 掛在 `.cover-stage`；去除 swipe 回饋的幾何在 `src/lib/cover-swipe-feedback.js`；`tests/cover-zoom.test.mjs`、`tests/lyrics-layout-freeze.test.mjs`）：滾輪（以游標為錨點）或雙指縮放，0.5–10 倍，雙擊恢復，放大後可平移（滑鼠拖曳、觸控雙指，夾在溢出量內）；只對封面套 `transform: translate scale`；佈局以 `--np-cover-width`／`--np-cover-height` × `--np-cover-reserve` 預留欄寬（窄版列高），最多佔卡片 65%；縮小時封面欄 fr 份額由 `coverShrinkShare` 收斂（`--np-art-col-a/-b`／`--np-art-row`），歌詞份額（`--np-lyr-*`）同量增加，兩軌 fr 總和固定為 2；倍率 1 不預留（`--np-cover-reserve` 0）。縮放中的封面以 `data-cover-zoomed` 屬性標記（不用 class），放大時另加 `data-cover-pannable`（滑鼠拖曳歸平移，見手勢）；基準尺寸用 1 倍時的 `coverBaseAvailable`；第二指以合成 pointercancel 取消第一指的滑動（`dispatchingCancel`）。直排／橫排只看長寬比例（`@media (orientation: portrait)` 直排，封面 1.1fr、歌詞 0.9fr）。狀態保存在 `coverZoomPersisted`（action 的 `initial`／`syncScale`）：縮小的封面切歌後維持，放大的切歌即還原；跨重啟只記縮小（`settings.json` 的 `coverZoom.scale` 0.5–1，`settings_get/set_cover_zoom`，300 ms 去抖；`coverBaseReady` 前忽略）。

縮放效能設計（每一步都要跑滿更新率）：（1）輸入合併：滾輪因子相乘、兩指與拖曳只記最新位置，由一個 rAF 回呼套用（`frame()`）；該回呼開頭只讀一次 `getBoundingClientRect`（此時版面是乾淨的，不強制重排，`coverGeometry` 由同一個 rect 取得視覺中心、版面中心與未縮放尺寸），之後只寫（transform、data 屬性、`onZoom`）。（2）錨點是絕對的：`anchoredZoom` 以「內容點 u 要落在游標／手指中點」直接求出 translate，所以上一步的版面位移（欄寬改變使封面版面中心移動）在同一次寫入就被吸收；滾輪連續動作沿用同一個 u（游標移動超過 2 px 才重取），倍率改變會擠壓版面（歌詞欄），此版面變動在同一次 rAF 回呼內的 microtask（`settleLayout`＝Svelte `tick`，仍在繪製之前）提交後，`repin()` 再讀一次、以同一個內容點 u 重新釘錨，所以沒有任何一幀以未補償的位置繪出（先前排下一個 rAF 重新釘錨，每個縮放步驟會多畫一幀偏移）；每幀最多兩次讀（第二次是版面本來就要做的強制重排）、兩次寫。（3）即時擠壓：預留欄寬變數隨每步更新（`--np-cover-reserve` 在卡片 65% 夾限之上取 `coverReserve` 的上界，超過夾限後值不再變，不觸發樣式重算；`--np-cover-zoom` 已移除；變數留在唯一子節點為卡片的 `.now-playing-view`，移到卡片本身沒有收益）。（4）歌詞文字版面凍結：`coverZoom` 的 `onZoomingChange(true)` 在第一步發出，輸入停止 `COVER_ZOOM_SETTLE_MS`（50 ms，使用者定案；這是等待不是動畫）後發 `false`；`LyricsView` 的 `layoutFrozen` 期間忽略 ResizeObserver、不重建 `buildLyricsLayout`／不重新量列高與卡拉 OK，列寬以 `--lyrics-frozen-width` 固定為上次穩定的 `layoutWidth`，視窗只裁切；結束時 `layoutFrozen` 轉 false，一次取新寬高、重排並即時重新置中。重排就地更新既有列：時間軸與純歌詞的列只以行索引為 key（不含 layout generation），generation 以 `observeLyricRow` 的參數傳入讓列重新標記並量測，所以重排不會整批重建 DOM（Android 上新建的列來不及點陣化，歌詞區會空白約 2 幀）。`.lyrics-lines-viewport` 套 `contain: layout paint`，且一律 `overflow-x: hidden; overflow-y: auto`（凍結結束不改任何捲動容器屬性），封面與格線變化不使歌詞子樹失效。沒有縮放時（視窗改變大小等）行為不變。（5）圖層結構固定：`.now-playing-view .cover-stage` 永久 `z-index: 1` 與 `will-change: transform`，任何手勢、動畫開始或結束都不新增、移除或重新堆疊圖層；`data-cover-zoomed` 只改版面（`max-width`／`max-height`／`flex`），`data-cover-resetting` 沒有樣式，`data-cover-gesture` 已移除。理由：先前在手勢結束 200 ms 後移除 `will-change`、並以 `data-cover-resetting`／`data-cover-zoomed` 切換 `z-index`，Android WebView 在圖層重建時要從頭點陣化封面與歌詞，錄影中封面與歌詞整片空白約 2 幀（Windows GPU 快所以看不出）。（6）清晰度：常駐 `will-change` 的圖層維持升級當時的光柵倍率，放大後本身是糊的；改由「重光柵微移」（re-raster nudge，`src/lib/cover-reraster.js` 的純函式與 `cover-zoom.js` 的 `runNudge`）處理，證據與規則見下方「封面清晰度」一節。不再用覆蓋 canvas 提供清晰度。（7）雙擊還原（FLIP，`COVER_RESET_MS` 200 ms、`ease`，使用者定案；跑在 stage 上，見下方「還原動畫跑在 stage 上」）：`reset()` 在同一個 task 內先讀目前繪出的矩形，立刻以 identity 提交最終版面（`apply`：清 transform、移除 `data-cover-zoomed`、`onZoom`，歌詞欄與預留欄寬在第 0 幀就定位），`await settleLayout()` 後量測新的未變形矩形，以 `flipTransform(from, to)` 求反向 transform，並在同一個 task（繪製之前）對 stage 啟動 Web Animation（`restoreGlide`）；沒有未補償的一幀。`ResizeObserver` 監看封面與其欄，若此幀的繪製前又有版面變動（App 自己的 observer），以同一起點與已過時間重新啟動動畫。reduced-motion 直接還原。驗收：Windows CDP 逐 rAF 讀 `.cover-stage` 的 `getBoundingClientRect`，任一幀位移不得超過一般滑動步長（200 ms 的 ease 曲線，120 Hz 時每幀最大約為總位移的 4%），第 0 幀必須與還原前的畫面重合；手機以螢幕錄影逐幀確認縮小途中無缺角、結束無閃一下或軟的一幀。量測方法：Windows CDP 在固定三段（1.0→1.3、1.5→6、1.0→0.5）送合成滾輪，比對 `Performance.getMetrics` 的 LayoutCount／RecalcStyleCount／LayoutDuration／ScriptDuration 增量、rAF 間隔直方圖與 LoAF；Android 以手動雙指縮放搭配 `gfxinfo framestats`。

手勢：`src/lib/swipe-dismiss.js`（`use:swipeDismiss`，測試 `tests/swipe-dismiss.test.mjs`）。觸控／筆超過 10 px 鎖定主軸，非關閉軸交還瀏覽器；從 input／select／textarea／`[role="slider"]`／`[data-swipe-ignore]` 開始的手勢忽略；跟手用 CSS `translate`，放開時位移 ≥ 30% 或速度 ≥ 0.5 px/ms 即觸發，否則 180 ms 彈回；滑動後吞一次 click；reduced-motion 不播動畫。綁定：窄版導覽面板左滑 → `closeNavPanel`，快速設定右滑 → `closeQuickSettings`；正在播放封面 `follow: false, damped: true`（橡皮筋約 24 px）：左滑（deltaX < 0）→ 下一首、右滑 → 上一首（使用者實測確認，勿對調）、下滑 → `closeNowPlaying`；歌詞區（`.now-playing-lyrics`，`touch-action: pan-y`）同樣左右切歌，回饋經 `feedbackTarget` 播在封面。滑鼠（`mouseActions`，僅主鍵）：整個 `.now-playing-view` 水平拖曳切歌，`.cover-stage` 向下拖曳收合；只有放大（倍率 > 1）時封面帶 `data-cover-pannable`（`isCoverPannable`，只是資料屬性、不改任何樣式），滑鼠在其上拖曳是平移；縮小或倍率 1 時滑鼠拖曳照常切歌與收合（`SWIPE_MOUSE_DRAG_OWNER_SELECTOR`；`data-cover-zoomed` 只管版面）；拖曳鎖定時清除文字選取（`getSwipeActionsFor`／`isSwipeMouseStart`）。

睡眠定時：播放頁頂欄「羅」與歌曲資訊（ⓘ）之間的鬧鐘按鈕（aria-label／tooltip「睡眠定時」，啟用時 `.is-active` 並在 tooltip 顯示剩餘時間）開啟向下的 `.floating-surface` 面板（定位共用 `getPopoverHorizontalShiftPx`），點外部或 Esc 關閉。hh:mm 顯示剩餘（向上取整、每秒更新）；小時、分鐘為兩個 `role="slider"` 欄位，上下拖曳（每 14 px 一格，`touch-action: none`）、滾輪（像素模式每 50 px）或方向鍵調整，各自夾住不進位（`adjustSleepTimerField`），上限 23:59（Rust `MAX_SLEEP_TIMER_MS`）；以手勢為單位凍結快照（`beginSleepTimerEdit`／`stepSleepTimerEdit`，滾輪／方向鍵 800 ms 無動作結束）；`sleep_timer_set` 回應以序號丟棄過期結果；> 0 啟動、0 或「取消定時」關閉。期限由 `src-tauri/src/sleep_timer.rs` 持有（epoch 毫秒截止＋世代號，每秒重讀系統時鐘），到期送 `sleep-timer-changed` 並 `playback_pause`；前端 `src/lib/sleep-timer.js` 只做顯示與換算。

換曲先備妥再切換：任何會開始另一首的操作（點曲目、專輯／演出者／播放清單／佇列播放、上一首／下一首〔畫面、通知欄、耳機、Windows SMTC、快捷鍵、手把〕、曲目自然結束）都先把新檔案開啟並驗證，成功才切換；失敗的載入絕不中斷正在播放的音樂。準備期間（遠端伺服器可能要數秒）狀態仍是播放中，播放列、佇列游標、正在播放頁、媒體工作階段中繼資料、位置與收聽時間都照舊；佇列游標、目前曲目、session 與播放次數只在成功時改變，失敗的曲目什麼都不計。決策都在 `player-core` 的 `track_start.rs`（純函式、可測）：`StartFailure`（`Unreachable`／`Unplayable`）與穩定訊息（`REMOTE_LINK_LOST`「伺服器無法連線」、`TRACK_UNPLAYABLE`「無法播放這首歌」、被取代為 `LOAD_SUPERSEDED`）；`NaturalWalk` 與 `natural_walk_cursors`。

手動開始（點選、上一首／下一首、任何使用者選擇）只試一次：失敗時什麼都不改，音樂照常播放，顯示會自動消失的通知（連不上伺服器＝「伺服器無法連線」，其他〔檔案不見、格式不支援、解碼或開檔錯誤〕＝「無法播放這首歌」），不會自動跳到下一首；原本沒有在播放（停止或空）時失敗，只顯示通知、維持原狀。自然結束則從下一首起依佇列走訪順序逐首各試一次，第一首成功的就開始，失敗不中止：單曲循環只重試同一首，全部循環繞整個佇列一圈（每首最多一次，最後才是剛結束的那首），不循環到最後一首為止；某伺服器（帳號）被判定連不上（`Network` 錯誤或不可達退避，見 ADR 0026）時，本輪其餘該伺服器的曲目直接略過、不等待——但整首都在磁碟快取的曲目不屬於任何伺服器（`player_core::walk_server_key` 查 `RemoteContent::available_offline`），不會被略過，手動點選、Windows 探測與 Android 預檢也都直接從快取開啟成功（見 ADR 0026 快取優先），只有未快取的曲目在伺服器離線時失敗。全部失敗就停在結尾（Windows 為 `Ended`、Android 為 `ended`，和一般結束相同）並通知最相關的失敗（連不上伺服器優先）。走訪被使用者的任何新選擇取消（最新選擇勝出，見 `playback-command-order.js`）；失敗的曲目不改變隨機權重或統計。

跳到結尾＝自然結束：每次 seek 都夾在 0..曲長（前端 `normalizeSeekPositionMs`；Rust `playback_seek` 再夾一次：Windows `seek_playback` 以 `player_core::clamp_seek` 依 worker 的曲長，Android actor 以 `clamp_seek_ms` 依原生或曲庫曲長〔`known_duration_ms`〕；Kotlin `seek` 也夾在 `player.duration` 內）。目標在結尾或之後（`player_core::plan_seek` 回 `EndOfTrack`）就當成曲目自然播完；「結尾」是快照回報的整數毫秒曲長（`duration_millis` 無條件捨去），解碼器的實際曲長通常多出不到 1 ms，所以 seek 到回報的曲長也算結尾（先前只比實際曲長，暫停中 seek 到回報曲長會變成一般 seek、停在最後不到 1 ms 處而不換曲；播放中則因立刻播完而看不出來）：Windows worker 的 `end_track_by_seek` 停止輸出、快照設 `Ended`（位置＝曲長、沒有錯誤），`playback_seek` 立刻呼叫 `advance_ended_queue`（不等下一次輪詢）；Android `end_track_by_seek` 先送原生 `pause` 與 `seek` 到曲長（沒有可開始的項目時，播完的歌留在結尾、不再出聲，之後按播放會立刻再結束一次），再跑 `start_after_natural_end`。之後完全是上述自然結束的走訪（佇列順序、循環模式、先備妥再切換），只差是否播放（使用者定案）：播放中拖到結尾，下一首照常播放；沒有在播放（暫停等）時，走訪開始的那一首停在開頭、維持暫停。Windows 由 worker 快照的 `ended_while_paused`（`end_track_by_seek` 依 seek 前的狀態設定，曲目自然播完與載入成功時清除）傳給 `advance_ended_queue`，它以 `prepare_track_load(…, false)` 載入，`LoadPreservingPlayback` 看到 `Ended`＋`ended_while_paused` 就設為 `Paused`；Android `end_track_by_seek` 依 `counts_as_playing` 呼叫 `walk_after_end(…, play)`，載入指令帶 `playWhenReady: false`。走訪什麼都開始不了時，照樣停在結尾（`Ended`／`ended`）、沒有錯誤。Android 另記 `ended_by_seek`（該次 load instance），之後 ExoPlayer 對同一項目送來的 `ended` 事件不再當成第二次自然結束。解碼器在檔案尾端無法 seek 也算結束：Symphonia 的 FLAC demuxer 對最後一個樣本（目標＝`n_frames`）線性搜尋找不到包含它的 frame，讀到檔尾回 `UnexpectedEof`（rodio 轉成 `AudioError::Seek`），實機在最後一個 frame 內也可能如此；worker 收到 `AudioError::Seek` 且目標距結尾不超過 `SEEK_TAIL_WINDOW`（2 秒，大於 FLAC 最長 frame 65,535 樣本／44.1 kHz≈1.5 秒）時同樣走 `end_track_by_seek`（`seek_failure_ends_track`），其他位置的 seek 失敗維持原本的錯誤。Android 轉換來源（`moedsd`／`moewv`／`moeflac`）的 `read_at` 在尾端回傳剩下的位元組、在結尾回 0（`player-flac` 的 `seek_to_frame` 對結尾直接標記 ended），ExoPlayer 的 WAV seek map 也夾在最後一個區塊，不會在尾端出錯。決策是 `player-core` 的 `seek.rs`（純函式）。測試：`seek::tests`；`player-audio-windows` 的 `a_seek_to_or_past_the_end_ends_the_track_without_an_error`、`a_failed_seek_in_the_tail_ends_the_track_and_elsewhere_stays_an_error`、`a_seek_to_the_end_while_paused_ends_the_track_and_the_next_load_stays_paused`、`decoders_that_refuse_a_seek_do_so_only_in_the_tail`；`windows_library_integration_tests` 的 `a_seek_to_the_end_while_*`、`a_paused_seek_to_the_reported_duration_*`（測試後端的曲長刻意多 0.4 ms）、`play_after_a_paused_seek_just_before_the_end_*`；`android_playback::integration_tests` 的 `a_seek_past_the_end_is_the_end_of_the_track_*`、`a_seek_to_the_end_while_paused_loads_*`、`after_a_seek_to_the_end_the_service_ended_event_*`、`a_seek_to_the_end_with_nothing_to_go_on_to_*`、`a_seek_just_before_the_end_*`；`player-flac` 的 `the_wav_stream_jumps_into_the_last_frame_and_to_the_end`。Android 實機已驗證播放中與暫停中跳到結尾；未驗證：Windows Release 實機（含 DSEE HX、獨佔模式）。

通知的送達：被拒絕的指令回傳穩定訊息（`playback_play`、`playback_next`、`playback_previous` 的 `Err`），前端 `sendPlaybackCommand` 以 `classifyStartError` 分類並顯示通知，被取代的啟動（`superseded`）不顯示；不是由畫面發起的啟動（耳機鍵、通知欄、SMTC、曲目結束後的走訪）沒有可拒絕的指令，所以快照帶 `startFailure`（`kind` 與遞增的 `sequence`），前端 `readStartFailure` 每個編號只通知一次（首張快照只設基準，重載頁面不重播舊失敗）；兩條路徑 2 秒內的同一次失敗只出現一次（`start-failure-notice.js`）。

Windows：`AudioBackend::load` 的合約是失敗時原本載入的曲目維持不變（`RodioBackend` 先開解碼器才動 `TrackPlayer`；`ExclusiveBackend::load` 先開一次解碼器再 `reset_for_load`），worker 的 `load_track` 失敗時不改快照（沒有載入任何曲目時才在開檔期間顯示 `Loading`），也不動收聽計時。遠端檔案（`moeremote://` 偽路徑）另由 `AudioBackend::probe` 回傳的檢查函式在 `moe-audio-probe` 輔助執行緒上開檔（`begin_load_abandonable` 讓它與被取代的載入一樣能被中止；`remote_input::probing` 讓它的讀取失敗不被誤認成正在播放那首的串流斷線），worker 這段時間照常處理暫停、seek、音量與位置更新，檢查通過才在 worker 上執行真正的載入（遠端的磁碟快取讓第二次開檔不連網）；較新的載入取代等待中的檢查，Stop 取消它，15 秒（`LOAD_PREPARE_DEADLINE`）仍無回應就放棄並回報連不上伺服器；應用層（`src-tauri/src/lib.rs`）等待播放命令回應最多 20 秒（`TRACK_LOAD_WAIT`）。自然結束的走訪在 `advance_ended_queue`（由 `playback_get_snapshot` 的輪詢啟動，`queue_advance_pending` 避免重複；全部失敗時旗標維持到離開 `Ended`，不會每次輪詢重走），每次請求前在 `command_gate` 內檢查使用者沒有新的載入（`LoadCounter::requested`／`in_flight`）。

Android：Media3 的 `ExoPlayer.setMediaItem` 會立刻拆掉正在播放的項目，沒有可以預先備妥再切換的副播放器，所以改用預檢：`PlaybackService` 在動 ExoPlayer 之前，由 `MediaPreflight`（`preflightExecutor` 的工作執行緒）用與播放相同的 `DsdAwareDataSourceFactory` 開檔（`file://`、`content://`、`moedsd://`、`moewv://`、`moeremote://` 走各自的資料來源，遠端經 `nativeOpen` 與磁碟快取），再用 `DefaultExtractorsFactory` 的 extractor `sniff` 辨識容器（與 ExoPlayer 選 extractor 的方式相同）；通過才執行原本的載入流程（封面準備、`setMediaItem`），失敗則 ack 帶 `error` 與 `retained: true`（播放器完全沒被動到），Rust 看到 `retained` 就不使 native 快照失效。檢查最多 12 秒（`PREFLIGHT_TIMEOUT_MS`，短於 Rust 等待的 15 秒），遠端逾時視為連不上。Rust 放棄等待一個載入（被新選擇取代或逾時）時送 `cancel_load`（`targetCommandId`），`LoadPreflightGate` 讓尚在檢查的舊載入完成後不再切換；較新的載入永遠取代舊的。`PlaybackCommandGate.mayPreempt` 讓檢查中的載入不擋住下一個指令。Rust `android_playback.rs`：`start_entry` 是切到佇列項目的唯一位置（成功才改游標、目前曲目與 session），`start_after_natural_end` 是走訪，`start_error` 把手動開始的錯誤轉成穩定訊息並記入快照；收聽計時在成功時才封存舊曲（`seal_outgoing_segment` 用等待期間排隊的最新快照），失敗不動計時。檢查通過後 ExoPlayer 自己的解碼器若仍失敗（極少見），維持原行為（舊項目已被取代，`invalidate_failed_load`）。測試：`track_start::tests`、`player-audio-windows` 的 `a_load_that_fails_*`、`a_remote_file_that_cannot_be_reached_*`、`while_a_server_is_asked_*`、`a_server_that_never_answers_*`、`stop_drops_a_choice_*`；`windows_library_integration_tests` 的 `a_manual_start_that_fails_*`、`when_a_track_ends_the_walk_*`、`when_no_entry_loads_*`、`repeat_one_retries_*`；`android_playback::integration_tests` 的 `a_load_the_service_refuses_*`、`a_server_that_cannot_be_reached_*`、`when_a_track_ends_the_walk_*`、`when_every_entry_fails_*`、`repeat_one_retries_*`、`a_choice_of_the_user_ends_the_walk_*`；`PlaybackProtocolStateTest`（`LoadPreflightGate`、`mayPreempt`）；`tests/start-failure-notice.test.mjs`。未驗證：Release 實機（手機播放本機 A、點連不上的遠端 B，A 要繼續播放並出現通知；再點本機 C 要切換）、Windows 真實遠端伺服器、獨佔模式與 DSEE HX 在檢查通過後才失敗的極少數情況（舊曲目可能已被停止）。

### 封面清晰度：重光柵微移（取代高解析覆蓋 canvas）

問題：`.cover-stage` 是永久 `will-change: transform` 的合成層（硬性規則，不得切換），Chrome 以升級當時的倍率光柵化它。Android 手機的 LayerTree 看到 998×998 px 的圖層套 7.1 倍 transform，所以放大後的封面是糊的。

實驗（以暫時 CDP 腳本在 Android 手機驗證，覆蓋 canvas 隱藏）：在 stage 上做滑動回饋（translate／scale／opacity 的 transition）之後，Chrome 會以當下倍率重新光柵化該圖層，封面變清晰。拆解：A（translate 6px＋scale 0.97＋opacity 0.86，180 ms transition）→ 清晰；B（只有 opacity）→ 無變化；C（只有 translate 6px）→ 清晰；F（只有 translate 0.01px，180 ms transition）→ 清晰；另外 D（只有 scale 0.97）、E（translate 1px＋scale 0.999＋opacity 0.99）、G（translate 0.5px）在同一組實驗中（暫時腳本 nudgetest.mjs）；直接寫入 `scale`（1.000001–1.0005）或以 Web Animation 動畫它（1–80 ms）都不能穩定觸發重光柵。結論：translate 的 CSS transition 即可觸發，位移量小到 0.01 px 也有效且肉眼不可見。

規則（使用者核准）：放大（倍率 > 1）且穩定（倍率變化不超過 0.0005）`COVER_LAYER_IDLE_MS`（50 ms，計時器容許 2 ms 提早）、且沒有手指／滾輪／swipe 回饋時，對 stage 做一次微移：inline `translate: 0.01px 0px` 與 `transition: none`，強制樣式計算，下一幀改為 `transition: translate 180ms` 並清掉 translate，約 260 ms 後還原先前的 transition 字串。之後每次倍率變化再度穩定都再做一次（平移不改倍率則不做）；倍率 ≤ 1 不做；換歌新圖載入（`load`、class、src、childList）與播放頁重新開啟會重設「已微移」狀態，倍率仍 > 1 時再微移一次。手勢開始（pointerdown、滾輪、套用 transform）取消尚未執行或進行中的微移並只收回自己寫的值；swipe 回饋蓋過進行中的微移時（以 MutationObserver 與第二步的屬性比對偵測）微移放棄、不清除回饋的任何屬性，restore 計時器只在 transition 仍是自己寫的字串時才還原。減少動態偏好不改變行為：位移只有百分之一像素。除錯：`localStorage['moe.debug.coverSwipe']='1'` 時每次微移記錄 `[cover-reraster]`。

殘留指標清理規則：`cover-zoom.js` 的 `pointers` 只要非空就算手勢進行中（重光柵微移會一直等待），但滑鼠按下後若放開發生在封面節點之外（拖出節點或視窗、或被 swipe-dismiss 等其他處理器捕獲指標），節點收不到 pointerup，條目會殘留而使微移永遠不再觸發。因此 (1) 在 `window` 以捕獲階段監聽 `pointerup`／`pointercancel`，對追蹤中的滑鼠條目走同一個 `up()` 流程（平移、雙指、`zoomGate`、`scheduleReraster` 收尾一致，已移除的 id 直接忽略，所以與節點自己的監聽並存是冪等的）；(2) `pointermove` 時若滑鼠條目的 `buttons === 0` 就視為已放開，同樣走 `up()`。只對 `pointerType === 'mouse'`（條目記錄 `type`）；觸控與筆由系統捕獲到接觸點，`buttons` 為 0 不代表放開，不受影響。判斷規則是純函式（`src/lib/cover-pointers.js`，`tests/cover-pointers.test.mjs`）；`destroy()` 移除這兩個 window 監聽。

覆蓋 canvas 的清晰度繪製已移除，連帶消除了兩個問題：swipe 彈回結束時的閃一下（canvas 與 stage 的接手時機），以及第一次滑動前的一次性模糊（尚未畫過覆蓋層）；雙擊還原動畫的覆蓋 canvas 也已移除，見下一節。

### 還原動畫跑在 stage 上；覆蓋 canvas 已移除

決定（使用者核准）：雙擊還原（從放大或縮小）不再畫縮圖大小的 canvas 複本，改由 stage 自己動畫。流程：（1）讀還原前繪出的矩形；以 identity 一次提交最終版面（FLIP 規則不變，`settleLayout` 後量測新的未變形矩形，沒有未補償的一幀）；（2）同一個 task 內對 stage 啟動 `stage.animate([反向 transform, translate(0px, 0px) scale(1)], { duration: 200, easing: 'ease', fill: 'none' })`（`restoreGlide`，關鍵影格與 `flipTransform` 皆為純函式；第一個影格就是反向 transform，所以不另寫 inline transform）；（3）動畫結束或被取消時（`endGlide`）清掉所有自己設的值：`fill: none` 使動畫不留任何值，inline transform 對齊真正的最終狀態（identity 為空字串）；（4）動畫中滾輪或手指按下（`interruptGlide`）：先讀目前繪出的矩形（含動畫）、取消動畫，再以 `stateFromVisual` 求出能畫出同一個矩形的縮放狀態（倍率 ≤ 1 時無法帶位移，會回到版面中心；放大時夾在溢出量內）套用，`settleLayout` 後再以版面實際位置重新釘住（和縮放步驟的 `repin` 同一做法），所以沒有跳動；已到達 identity 的接手不產生縮放狀態；（5）換歌時元件被銷毀，`destroy` 取消動畫並清旗標；（6）圖層規則不變：只動畫 transform，從不切換 `will-change`、`z-index`、`contain`、`isolation`、`position`；常駐 canvas、`data-cover-overlay`、`.cover-stage-overlay` 與 `.now-playing-artwork { position: relative }`（只為 canvas 而設）一併刪除，`cover-overlay.js` 只剩 swipe 回饋幾何，改名 `cover-swipe-feedback.js`。

清晰度推論：還原結束在倍率 1，不需要重光柵微移。放大 → 1 是把已高解析（微移後）的圖層縮小，縮小永遠清晰；縮小（如 0.5）→ 1 是把以倍率 1 光柵化的圖層放回 1，也清晰。

已知風險（需手機驗證）：先前改用 canvas 的理由仍在——Chromium 對正在跑 transform 動畫的圖層會依動畫最大倍率決定光柵倍率，放大 → 1 的動畫在手機上可能要求約 3000 裝置像素見方的 tile，動畫途中還沒進入畫面的 tile 可能缺角或軟。使用者要求以 stage 動畫取代 canvas；若手機錄影仍見缺角，再另案處理（例如縮短動畫的最大倍率範圍），不要恢復 canvas。
