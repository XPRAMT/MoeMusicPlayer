# 播放頁互動：封面縮放、手勢、睡眠定時與播放鍵狀態

Status: 已採納

## Context

播放頁的封面縮放、觸控／滑鼠手勢、睡眠定時與 seek 期間播放鍵的行為原本只記在 AGENTS.md，沒有對應的 ADR。此 ADR 記錄其目前設計。

## 目前設計

播放鍵與 seek 期間：`PlaybackService.kt` 的 `playbackStateName` 在 `playWhenReady && STATE_BUFFERING && 有項目` 時回 `"buffering"`（快照節流看 `playWhenReady`）；Rust `android_playback.rs` 的 `counts_as_playing`（playing／buffering）決定 `is_playing`、`resumePlayback` 與換曲 `play_when_ready`，收聽計時只算 `"playing"`；前端 `PlaybackState` 有 `buffering`，播放時鐘與現場播放次數只在 `playing` 前進。seek 走 `sendPlaybackCommand(..., { seek: true })`（設 `isSeeking`）；點擊處理在 `isSendingPlaybackCommand || isSeeking` 時忽略但外觀不變（從清單選曲例外：不看忙碌旗標、最新選擇勝出，見 `playback-command-order.js`）；上一首／下一首 `disabled` 只看 `playbackNavigationReady` 與有無上／下一首；播放、隨機、循環在其他指令忙碌時 disabled。測試：`tests/seek-transport-lock.test.mjs`、`PlaybackProtocolStateTest.aSeekWhilePlayingIsBufferingNotAPause`（`src-tauri/gen/android` 下 `gradlew :tauri-plugin-media-index:testDebugUnitTest`）、`android_playback::integration_tests::a_seek_buffering_snapshot_keeps_playing_without_flipping_resume_or_counting_time`。

正在播放封面縮放（`src/lib/cover-zoom.js`，action `coverZoom` 掛在 `.cover-stage`；覆蓋 canvas 的幾何在 `src/lib/cover-overlay.js`；`tests/cover-zoom.test.mjs`、`tests/lyrics-layout-freeze.test.mjs`）：滾輪（以游標為錨點）或雙指縮放，0.5–10 倍，雙擊恢復，放大後可平移（滑鼠拖曳、觸控雙指，夾在溢出量內）；只對封面套 `transform: translate scale`；佈局以 `--np-cover-width`／`--np-cover-height` × `--np-cover-reserve` 預留欄寬（窄版列高），最多佔卡片 65%；縮小時封面欄 fr 份額由 `coverShrinkShare` 收斂（`--np-art-col-a/-b`／`--np-art-row`），歌詞份額（`--np-lyr-*`）同量增加，兩軌 fr 總和固定為 2；倍率 1 不預留（`--np-cover-reserve` 0）。縮放中的封面以 `data-cover-zoomed` 屬性標記（不用 class），放大時另加 `data-cover-pannable`（滑鼠拖曳歸平移，見手勢）；基準尺寸用 1 倍時的 `coverBaseAvailable`；第二指以合成 pointercancel 取消第一指的滑動（`dispatchingCancel`）。直排／橫排只看長寬比例（`@media (orientation: portrait)` 直排，封面 1.1fr、歌詞 0.9fr）。狀態保存在 `coverZoomPersisted`（action 的 `initial`／`syncScale`）：縮小的封面切歌後維持，放大的切歌即還原；跨重啟只記縮小（`settings.json` 的 `coverZoom.scale` 0.5–1，`settings_get/set_cover_zoom`，300 ms 去抖；`coverBaseReady` 前忽略）。

縮放效能設計（每一步都要跑滿更新率）：（1）輸入合併：滾輪因子相乘、兩指與拖曳只記最新位置，由一個 rAF 回呼套用（`frame()`）；該回呼開頭只讀一次 `getBoundingClientRect`（此時版面是乾淨的，不強制重排，`coverGeometry` 由同一個 rect 取得視覺中心、版面中心與未縮放尺寸），之後只寫（transform、data 屬性、`onZoom`）。（2）錨點是絕對的：`anchoredZoom` 以「內容點 u 要落在游標／手指中點」直接求出 translate，所以上一步的版面位移（欄寬改變使封面版面中心移動）在同一次寫入就被吸收；滾輪連續動作沿用同一個 u（游標移動超過 2 px 才重取），倍率改變會擠壓版面（歌詞欄），此版面變動在同一次 rAF 回呼內的 microtask（`settleLayout`＝Svelte `tick`，仍在繪製之前）提交後，`repin()` 再讀一次、以同一個內容點 u 重新釘錨，所以沒有任何一幀以未補償的位置繪出（先前排下一個 rAF 重新釘錨，每個縮放步驟會多畫一幀偏移）；每幀最多兩次讀（第二次是版面本來就要做的強制重排）、兩次寫。（3）即時擠壓：預留欄寬變數隨每步更新（`--np-cover-reserve` 在卡片 65% 夾限之上取 `coverReserve` 的上界，超過夾限後值不再變，不觸發樣式重算；`--np-cover-zoom` 已移除；變數留在唯一子節點為卡片的 `.now-playing-view`，移到卡片本身沒有收益）。（4）歌詞文字版面凍結：`coverZoom` 的 `onZoomingChange(true)` 在第一步發出，輸入停止 `COVER_ZOOM_SETTLE_MS`（50 ms，使用者定案；這是等待不是動畫）後發 `false`；`LyricsView` 的 `layoutFrozen` 期間忽略 ResizeObserver、不重建 `buildLyricsLayout`／不重新量列高與卡拉 OK，列寬以 `--lyrics-frozen-width` 固定為上次穩定的 `layoutWidth`，視窗只裁切；結束時 `layoutFrozen` 轉 false，一次取新寬高、重排並即時重新置中。重排就地更新既有列：時間軸與純歌詞的列只以行索引為 key（不含 layout generation），generation 以 `observeLyricRow` 的參數傳入讓列重新標記並量測，所以重排不會整批重建 DOM（Android 上新建的列來不及點陣化，歌詞區會空白約 2 幀）。`.lyrics-lines-viewport` 套 `contain: layout paint`，且一律 `overflow-x: hidden; overflow-y: auto`（凍結結束不改任何捲動容器屬性），封面與格線變化不使歌詞子樹失效。沒有縮放時（視窗改變大小等）行為不變。（5）圖層結構固定：`.now-playing-view .cover-stage` 永久 `z-index: 1` 與 `will-change: transform`，任何手勢、動畫開始或結束都不新增、移除或重新堆疊圖層；`data-cover-zoomed` 只改版面（`max-width`／`max-height`／`flex`），`data-cover-resetting` 沒有樣式，`data-cover-gesture` 已移除。理由：先前在手勢結束 200 ms 後移除 `will-change`、並以 `data-cover-resetting`／`data-cover-zoomed` 切換 `z-index`，Android WebView 在圖層重建時要從頭點陣化封面與歌詞，錄影中封面與歌詞整片空白約 2 幀（Windows GPU 快所以看不出）。（6）清晰度：常駐 `will-change` 的圖層維持升級當時的光柵倍率，放大後本身是糊的，所以由一個常駐的覆蓋 canvas（`cover-zoom.js` 建立、放在封面欄 `.now-playing-artwork` 內，`.cover-stage-overlay`，自己的圖層、`pointer-events: none`、只以 opacity 顯示／隱藏，隱藏時 backing 縮成 1×1）負責：最後一次輸入 `COVER_LAYER_IDLE_MS`（50 ms，使用者定案；這是等待不是動畫）後，只要倍率不是升級時的倍率（`coverOverlayWanted`：倍率 ≠ 1，或倍率 1 但升級時 ≠ 1，例如縮小狀態下開頁或換歌後還原），就把封面「看得見的部分加一圈邊界」（看得見的部分＝封面繪出矩形與所有裁切祖先、視窗的交集，`clipToAncestors`；邊界由 `overlayDrawRegion` 決定：四邊同寬地向外擴，夾在封面自己的繪出矩形內，碰到封面邊緣的那一邊停住、其他邊繼續長，直到總面積達看得見部分的 `COVER_OVERLAY_MARGIN_PIXEL_RATIO`＝2 倍裝置像素，且每邊不超過 `COVER_OVERLAY_MAX_DIMENSION`＝4096 裝置像素〔看得見的部分本身已超過時不加邊界〕；canvas 與封面同在 `.now-playing-artwork` 內，超出裁切祖先的部分被同樣的祖先裁掉；之後對齊裝置像素 `snapRectToDevicePixels`）以裝置解析度、從原圖解析度的解碼圖畫進 canvas（`cover-overlay.js` 的 `coverDrawPlan`：`object-fit: cover` 加 1 px 外擴的對應、平移、圓角裁切隨倍率放大），畫完才在同一個 task 顯示（重畫時直接取代舊內容，同一個 task 內完成），舊畫面一直留到那時；不會有超大圖層。任何輸入（按下指標、滑鼠或雙指平移、縮小、放大）都不隱藏覆蓋層（使用者定案）：canvas 記住它畫的時候封面的繪出矩形、自己的 client 矩形與封面欄的位置，之後每次封面 transform 改變，就以 `overlayFollowTransform` 求出讓 canvas 內容與封面同步的 translate＋scale（canvas 的 transform-origin 設在封面的版面中心〔`overlayOrigin`，見下方滑動回饋〕，translate 依此原點換算：繞中心 K 的 translate(a) scale(k) 等於繞原點 O 的 translate(a＋(1−k)(K−O)) scale(k)；內容映射 p′＝現在繪出矩形左上＋(p − 當時繪出矩形左上) × 倍率比；欄位移動的量另外抵銷，因為 canvas 定位在欄內），只寫 canvas 的合成器 `transform`，不重畫、不多讀版面。寫入點與封面自己的 transform 相同：`frame()` 內（封面 rect 與欄 rect 在幀開頭同一個乾淨時點讀，欄 rect 只在覆蓋層顯示時讀），`repin()` 內（`settleLayout` 提交擠壓後、封面重新釘錨的同一個 task），以及封面或欄的 ResizeObserver 回呼（版面之後、繪製之前，讀取不強制重排），所以縮小時歌詞區擠壓改變版面的那一幀，canvas 與封面也一致。理由：覆蓋層畫的倍率高於升級時倍率，放大時拉伸它仍比封面本身的圖層清晰，而放大只會顯示已畫範圍的一部分；平移或縮小露出、超出已畫範圍的地方顯示下方照常繪製的封面（較軟），直到靜止 50 ms 後以新倍率重畫。例外：還沒畫過清晰覆蓋層時（例如從 1 倍第一次縮放）就是封面本身。靜止時倍率等於升級時倍率（`coverOverlayWanted` 為 false）則隱藏覆蓋層。滑動回饋（使用者定案「甲」）：封面同時掛著 `swipeDismiss`（`follow: false, damped: true`；歌詞區與整個播放頁的 swipe 以 `feedbackTarget` 把回饋寫在封面），觸控時第一指在第二指落下前先移動就會鎖定主軸並在封面寫入 inline `translate`／`scale`／`opacity`（`transition: none`），第二指落下時 `coverZoom` 的合成 pointercancel 讓 swipe 以 `translate 180ms …` 的 transition 彈回並清空，180 ms 後的 setTimeout 再寫 `transition = ''`；縮放的每一幀 `apply()` 也會寫 `transition: none`。這四個屬性在封面上的每次變化，都由 MutationObserver 回呼（`observeCoverChanges` 的 `onStyle` → `mirrorFeedback`，在繪製前）原樣複製到覆蓋 canvas（同值、同 transition，覆蓋層顯示時 opacity 取封面的回饋 opacity），不隱藏覆蓋層。對齊：CSS 依序套 translate、rotate、scale、transform，全都繞 transform-origin；封面的 origin 是它的版面中心 C，所以回饋在 client 座標是 p → C＋t＋s(q − C)（q 為沒有回饋時的繪出位置）。canvas 的 transform-origin 設成同一個 C（以 canvas 自己的盒子座標表示，`overlayOrigin`，每次繪製與跟隨時更新），跟隨 transform 依此原點換算（見上），所以 canvas 也是 p → C＋t＋s(q − C)，兩者像素一致，含已有跟隨 transform 時。所有幾何讀取（`frame()`、`repin()`、resize、靜止重畫）改用 `stageRect()`：`getBoundingClientRect` 會包含個別的 translate／scale，所以在可能有回饋時（inline 有值或 transition 含 translate／scale）於 rect 讀取之後（樣式已乾淨）讀一次 computed（transition 進行中的目前值）並以 `withoutSwipeFeedback` 去除。靜止重畫時若封面仍有回饋，就以去除回饋的幾何畫，mirrored 的回饋照樣疊在新畫面上（而不是等回饋歸零才畫），所以 setTimeout 的 `transition = ''` 落在 50 ms 重畫之後也不會隱藏它。還原動畫期間（`resetting`）不複製回饋（`mirror(null)`），結束時再同步一次。`is-swiping` class 只在 `follow` 模式加上，封面的 swipe 是 `follow: false`，所以不會出現在封面上；它會改變合成（`will-change`、`contain`），若出現仍視為外來改變。限制：封面回饋 opacity < 1 時覆蓋層與其下照常繪製的封面各自半透明，疊起來比單獨的封面略不透明（opacity 0.85 時約 0.98）。封面在手勢以外被改變（App 寫入的其他 style、class、換圖 `src`、圖片 `load`、視窗 resize）立即隱藏並在靜止後重畫（MutationObserver 回呼在繪製前執行；「去除回饋屬性後的 inline style 等於 action 最後留下的」即為自己的 transform 寫入或滑動回饋，不算外來改變；觀察時帶 `attributeOldValue`，同一批記錄中某元素某屬性現在的值等於該批第一筆記錄的舊值〔沒有淨變化〕時，這些記錄一律忽略〔`unchangedInBatch`，class、style、src 都一樣〕，因為瀏覽器對沒有改變值的寫入也會產生記錄：swipe-dismiss 的 `up()` 在每次手指抬起與縮放開始的合成 pointercancel 都對封面 `classList.remove('is-swiping')`，封面本來就沒有這個 class，若算外來改變就會在每次抬指時隱藏覆蓋層、露出較軟的封面；沒有舊值的記錄仍算改變）；封面或欄的 resize 在覆蓋層顯示時改為對齊並在靜止後重畫，沒有覆蓋層時同前。記憶體：canvas backing 最多為看得見部分的 2 倍裝置像素（例如手機約 1100 裝置像素見方的可見區 → 約 2.4 百萬像素、RGBA 約 10 MB），隱藏時縮成 1×1。清晰覆蓋層下方的 `<img>` 照常繪製，讓它的 tile 為下一個手勢保持就緒；代價是含透明像素的封面在半透明處疊兩次（閒置放大時略深）。封面解碼圖不降採樣、不設 `image-rendering`；清晰度的上限是原圖解析度。（7）雙擊還原（FLIP，`COVER_RESET_MS` 200 ms、`ease`，使用者定案）：`reset()` 在同一個 task 內先讀目前繪出的矩形，立刻以 identity 提交最終版面（`apply`：清 transform、移除 `data-cover-zoomed`、`onZoom`，歌詞欄與預留欄寬在第 0 幀就定位），`await settleLayout()` 後量測新的未變形矩形，以 `flipTransform(from, to)` 求反向 transform；接著（仍在繪製之前）把整張封面以「符合螢幕解析度的縮圖大小」（倍率 1 時封面在螢幕上的尺寸 × devicePixelRatio，例如 340 CSS px × 3.25 ≈ 1105 裝置像素見方）畫進覆蓋 canvas、放在最終封面的位置，以 Web Animation 讓 canvas 從反向 transform 滑到 identity；封面本身不跑動畫、只隱藏它的 `<img>`（`data-cover-overlay` → `visibility: hidden`），滑動結束的同一個 task 隱藏 canvas、恢復 `<img>`。所以版面提交與補償在同一幀、沒有未補償的一幀（Windows 先前修正的閃動不回歸），縮小開始時略軟、結束時清晰。不直接對 `will-change` 封面跑縮小動畫的理由：Chromium 對正在跑 transform 動畫的圖層會依動畫的最大倍率重新決定光柵倍率（`will-change` 的「升級時倍率」黏性不保證壓過這個規則），手機上就是約 340 × 3 × 3.25 ≈ 3300 裝置像素見方的 tile 圖層，動畫期間還沒進入畫面的 tile 來不及點陣化，錄影中縮小途中出現缺角；canvas 是一張固定大小的貼圖，不分 tile、不受光柵倍率規則影響。不確定處：此保證的前提是 Android WebView 對這個 2D canvas 走 GPU 加速（貼圖圖層）；若裝置把它降為軟體 canvas，它會被畫進一般的 tile 圖層，仍可能依動畫倍率點陣化，需以手機錄影確認。沒有解碼圖（預設封面圖樣）時仍直接讓封面滑動（內容簡單）。`ResizeObserver` 監看封面與其欄，若此幀的繪製前又有版面變動（App 自己的 observer），以同一起點與已過時間重畫並重新啟動動畫。reduced-motion 直接還原。驗收：Windows CDP 逐 rAF 讀 `.cover-stage-overlay` 與 `.cover-stage` 的 `getBoundingClientRect`，任一幀位移不得超過一般滑動步長（200 ms 的 ease 曲線，120 Hz 時每幀最大約為總位移的 4%），第 0 幀 canvas 必須與縮放中的封面重合；平移與縮放中（含縮小時的歌詞區擠壓）逐 rAF 比對已顯示的 canvas 與封面的繪出矩形，內容對應的位置任一幀不得錯開；手機以螢幕錄影逐幀確認縮小途中無缺角、縮小後與縮放靜止後封面與歌詞無空白幀、放大靜止後封面清晰。量測方法：Windows CDP 在固定三段（1.0→1.3、1.5→6、1.0→0.5）送合成滾輪，比對 `Performance.getMetrics` 的 LayoutCount／RecalcStyleCount／LayoutDuration／ScriptDuration 增量、rAF 間隔直方圖與 LoAF；Android 以手動雙指縮放搭配 `gfxinfo framestats`。

手勢：`src/lib/swipe-dismiss.js`（`use:swipeDismiss`，測試 `tests/swipe-dismiss.test.mjs`）。觸控／筆超過 10 px 鎖定主軸，非關閉軸交還瀏覽器；從 input／select／textarea／`[role="slider"]`／`[data-swipe-ignore]` 開始的手勢忽略；跟手用 CSS `translate`，放開時位移 ≥ 30% 或速度 ≥ 0.5 px/ms 即觸發，否則 180 ms 彈回；滑動後吞一次 click；reduced-motion 不播動畫。綁定：窄版導覽面板左滑 → `closeNavPanel`，快速設定右滑 → `closeQuickSettings`；正在播放封面 `follow: false, damped: true`（橡皮筋約 24 px）：左滑（deltaX < 0）→ 下一首、右滑 → 上一首（使用者實測確認，勿對調）、下滑 → `closeNowPlaying`；歌詞區（`.now-playing-lyrics`，`touch-action: pan-y`）同樣左右切歌，回饋經 `feedbackTarget` 播在封面。滑鼠（`mouseActions`，僅主鍵）：整個 `.now-playing-view` 水平拖曳切歌，`.cover-stage` 向下拖曳收合；只有放大（倍率 > 1）時封面帶 `data-cover-pannable`（`isCoverPannable`，只是資料屬性、不改任何樣式），滑鼠在其上拖曳是平移；縮小或倍率 1 時滑鼠拖曳照常切歌與收合（`SWIPE_MOUSE_DRAG_OWNER_SELECTOR`；`data-cover-zoomed` 只管版面）；拖曳鎖定時清除文字選取（`getSwipeActionsFor`／`isSwipeMouseStart`）。

換曲先備妥再切換：任何會開始另一首的操作（點曲目、專輯／演出者／播放清單／佇列播放、上一首／下一首〔畫面、通知欄、耳機、Windows SMTC、快捷鍵、手把〕、曲目自然結束）都先把新檔案開啟並驗證，成功才切換；失敗的載入絕不中斷正在播放的音樂。準備期間（遠端伺服器可能要數秒）狀態仍是播放中，播放列、佇列游標、正在播放頁、媒體工作階段中繼資料、位置與收聽時間都照舊；佇列游標、目前曲目、session 與播放次數只在成功時改變，失敗的曲目什麼都不計。決策都在 `player-core` 的 `track_start.rs`（純函式、可測）：`StartFailure`（`Unreachable`／`Unplayable`）與穩定訊息（`REMOTE_LINK_LOST`「伺服器無法連線」、`TRACK_UNPLAYABLE`「無法播放這首歌」、被取代為 `LOAD_SUPERSEDED`）；`NaturalWalk` 與 `natural_walk_cursors`。

手動開始（點選、上一首／下一首、任何使用者選擇）只試一次：失敗時什麼都不改，音樂照常播放，顯示會自動消失的通知（連不上伺服器＝「伺服器無法連線」，其他〔檔案不見、格式不支援、解碼或開檔錯誤〕＝「無法播放這首歌」），不會自動跳到下一首；原本沒有在播放（停止或空）時失敗，只顯示通知、維持原狀。自然結束則從下一首起依佇列走訪順序逐首各試一次，第一首成功的就開始，失敗不中止：單曲循環只重試同一首，全部循環繞整個佇列一圈（每首最多一次，最後才是剛結束的那首），不循環到最後一首為止；某伺服器（帳號）被判定連不上（`Network` 錯誤或不可達退避，見 ADR 0026）時，本輪其餘該伺服器的曲目直接略過、不等待——但整首都在磁碟快取的曲目不屬於任何伺服器（`player_core::walk_server_key` 查 `RemoteContent::available_offline`），不會被略過，手動點選、Windows 探測與 Android 預檢也都直接從快取開啟成功（見 ADR 0026 快取優先），只有未快取的曲目在伺服器離線時失敗。全部失敗就停在結尾（Windows 為 `Ended`、Android 為 `ended`，和一般結束相同）並通知最相關的失敗（連不上伺服器優先）。走訪被使用者的任何新選擇取消（最新選擇勝出，見 `playback-command-order.js`）；失敗的曲目不改變隨機權重或統計。

跳到結尾＝自然結束：每次 seek 都夾在 0..曲長（前端 `normalizeSeekPositionMs`；Rust `playback_seek` 再夾一次：Windows `seek_playback` 以 `player_core::clamp_seek` 依 worker 的曲長，Android actor 以 `clamp_seek_ms` 依原生或曲庫曲長〔`known_duration_ms`〕；Kotlin `seek` 也夾在 `player.duration` 內）。目標在結尾或之後（`player_core::plan_seek` 回 `EndOfTrack`）就當成曲目自然播完；「結尾」是快照回報的整數毫秒曲長（`duration_millis` 無條件捨去），解碼器的實際曲長通常多出不到 1 ms，所以 seek 到回報的曲長也算結尾（先前只比實際曲長，暫停中 seek 到回報曲長會變成一般 seek、停在最後不到 1 ms 處而不換曲；播放中則因立刻播完而看不出來）：Windows worker 的 `end_track_by_seek` 停止輸出、快照設 `Ended`（位置＝曲長、沒有錯誤），`playback_seek` 立刻呼叫 `advance_ended_queue`（不等下一次輪詢）；Android `end_track_by_seek` 先送原生 `pause` 與 `seek` 到曲長（沒有可開始的項目時，播完的歌留在結尾、不再出聲，之後按播放會立刻再結束一次），再跑 `start_after_natural_end`。之後完全是上述自然結束的走訪（佇列順序、循環模式、先備妥再切換），只差是否播放（使用者定案）：播放中拖到結尾，下一首照常播放；沒有在播放（暫停等）時，走訪開始的那一首停在開頭、維持暫停。Windows 由 worker 快照的 `ended_while_paused`（`end_track_by_seek` 依 seek 前的狀態設定，曲目自然播完與載入成功時清除）傳給 `advance_ended_queue`，它以 `prepare_track_load(…, false)` 載入，`LoadPreservingPlayback` 看到 `Ended`＋`ended_while_paused` 就設為 `Paused`；Android `end_track_by_seek` 依 `counts_as_playing` 呼叫 `walk_after_end(…, play)`，載入指令帶 `playWhenReady: false`。走訪什麼都開始不了時，照樣停在結尾（`Ended`／`ended`）、沒有錯誤。Android 另記 `ended_by_seek`（該次 load instance），之後 ExoPlayer 對同一項目送來的 `ended` 事件不再當成第二次自然結束。解碼器在檔案尾端無法 seek 也算結束：Symphonia 的 FLAC demuxer 對最後一個樣本（目標＝`n_frames`）線性搜尋找不到包含它的 frame，讀到檔尾回 `UnexpectedEof`（rodio 轉成 `AudioError::Seek`），實機在最後一個 frame 內也可能如此；worker 收到 `AudioError::Seek` 且目標距結尾不超過 `SEEK_TAIL_WINDOW`（2 秒，大於 FLAC 最長 frame 65,535 樣本／44.1 kHz≈1.5 秒）時同樣走 `end_track_by_seek`（`seek_failure_ends_track`），其他位置的 seek 失敗維持原本的錯誤。Android 轉換來源（`moedsd`／`moewv`／`moeflac`）的 `read_at` 在尾端回傳剩下的位元組、在結尾回 0（`player-flac` 的 `seek_to_frame` 對結尾直接標記 ended），ExoPlayer 的 WAV seek map 也夾在最後一個區塊，不會在尾端出錯。決策是 `player-core` 的 `seek.rs`（純函式）。測試：`seek::tests`；`player-audio-windows` 的 `a_seek_to_or_past_the_end_ends_the_track_without_an_error`、`a_failed_seek_in_the_tail_ends_the_track_and_elsewhere_stays_an_error`、`a_seek_to_the_end_while_paused_ends_the_track_and_the_next_load_stays_paused`、`decoders_that_refuse_a_seek_do_so_only_in_the_tail`；`windows_library_integration_tests` 的 `a_seek_to_the_end_while_*`、`a_paused_seek_to_the_reported_duration_*`（測試後端的曲長刻意多 0.4 ms）、`play_after_a_paused_seek_just_before_the_end_*`；`android_playback::integration_tests` 的 `a_seek_past_the_end_is_the_end_of_the_track_*`、`a_seek_to_the_end_while_paused_loads_*`、`after_a_seek_to_the_end_the_service_ended_event_*`、`a_seek_to_the_end_with_nothing_to_go_on_to_*`、`a_seek_just_before_the_end_*`；`player-flac` 通知的送達：被拒絕的指令回傳穩定訊息（`playback_play`、`playback_next`、`playback_previous` 的 `Err`），前端 `sendPlaybackCommand` 以 `classifyStartError` 分類並顯示通知，被取代的啟動（`superseded`）不顯示；不是由畫面發起的啟動（耳機鍵、通知欄、SMTC、曲目結束後的走訪）沒有可拒絕的指令，所以快照帶 `startFailure`（`kind` 與遞增的 `sequence`），前端 `readStartFailure` 每個編號只通知一次（首張快照只設基準，重載頁面不重播舊失敗）；兩條路徑 2 秒內的同一次失敗只出現一次（`start-failure-notice.js`）。

Windows：`AudioBackend::load` 的合約是失敗時原本載入的曲目維持不變（`RodioBackend` 先開解碼器才動 `TrackPlayer`；`ExclusiveBackend::load` 先開一次解碼器再 `reset_for_load`），worker 的 `load_track` 失敗時不改快照（沒有載入任何曲目時才在開檔期間顯示 `Loading`），也不動收聽計時。遠端檔案（`moeremote://` 偽路徑）另由 `AudioBackend::probe` 回傳的檢查函式在 `moe-audio-probe` 輔助執行緒上開檔（`begin_load_abandonable` 讓它與被取代的載入一樣能被中止；`remote_input::probing` 讓它的讀取失敗不被誤認成正在播放那首的串流斷線），worker 這段時間照常處理暫停、seek、音量與位置更新，檢查通過才在 worker 上執行真正的載入（遠端的磁碟快取讓第二次開檔不連網）；較新的載入取代等待中的檢查，Stop 取消它，15 秒（`LOAD_PREPARE_DEADLINE`）仍無回應就放棄並回報連不上伺服器；應用層（`src-tauri/src/lib.rs`）等待播放命令回應最多 20 秒（`TRACK_LOAD_WAIT`）。自然結束的走訪在 `advance_ended_queue`（由 `playback_get_snapshot` 的輪詢啟動，`queue_advance_pending` 避免重複；全部失敗時旗標維持到離開 `Ended`，不會每次輪詢重走），每次請求前在 `command_gate` 內檢查使用者沒有新的載入（`LoadCounter::requested`／`in_flight`）。

Android：Media3 的 `ExoPlayer.setMediaItem` 會立刻拆掉正在播放的項目，沒有可以預先備妥再切換的副播放器，所以改用預檢：`PlaybackService` 在動 ExoPlayer 之前，由 `MediaPreflight`（`preflightExecutor` 的工作執行緒）用與播放相同的 `DsdAwareDataSourceFactory` 開檔（`file://`、`content://`、`moedsd://`、`moewv://`、`moeremote://` 走各自的資料來源，遠端經 `nativeOpen` 與磁碟快取），再用 `DefaultExtractorsFactory` 的 extractor `sniff` 辨識容器（與 ExoPlayer 選 extractor 的方式相同）；通過才執行原本的載入流程（封面準備、`setMediaItem`），失敗則 ack 帶 `error` 與 `retained: true`（播放器完全沒被動到），Rust 看到 `retained` 就不使 native 快照失效。檢查最多 12 秒（`PREFLIGHT_TIMEOUT_MS`，短於 Rust 等待的 15 秒），遠端逾時視為連不上。Rust 放棄等待一個載入（被新選擇取代或逾時）時送 `cancel_load`（`targetCommandId`），`LoadPreflightGate` 讓尚在檢查的舊載入完成後不再切換；較新的載入永遠取代舊的。`PlaybackCommandGate.mayPreempt` 讓檢查中的載入不擋住下一個指令。Rust `android_playback.rs`：`start_entry` 是切到佇列項目的唯一位置（成功才改游標、目前曲目與 session），`start_after_natural_end` 是走訪，`start_error` 把手動開始的錯誤轉成穩定訊息並記入快照；收聽計時在成功時才封存舊曲（`seal_outgoing_segment` 用等待期間排隊的最新快照），失敗不動計時。檢查通過後 ExoPlayer 自己的解碼器若仍失敗（極少見），維持原行為（舊項目已被取代，`invalidate_failed_load`）。測試：`track_start::tests`、`player-audio-windows` 的 `a_load_that_fails_*`、`a_remote_file_that_cannot_be_reached_*`、`while_a_server_is_asked_*`、`a_server_that_never_answers_*`、`stop_drops_a_choice_*`；`windows_library_integration_tests` 的 `a_manual_start_that_fails_*`、`when_a_track_ends_the_walk_*`、`when_no_entry_loads_*`、`repeat_one_retries_*`；`android_playback::integration_tests` 的 `a_load_the_service_refuses_*`、`a_server_that_cannot_be_reached_*`、`when_a_track_ends_the_walk_*`、`when_every_entry_fails_*`、`repeat_one_retries_*`、`a_choice_of_the_user_ends_the_walk_*`；`PlaybackProtocolStateTest`（`LoadPreflightGate`、`mayPreempt`）；`tests/start-failure-notice.test.mjs`。未驗證：Release 實機（手機播放本機 A、點連不上的遠端 B，A 要繼續播放並出現通知；再點本機 C 要切換）、Windows 真實遠端伺服器、獨佔模式與 DSEE HX 在檢查通過後才失敗的極少數情況（舊曲目可能已被停止）。

### 覆蓋 canvas 的放手（彈回）規則

拖曳中 canvas 複製 stage 的回饋以同步移動；放手時 stage 以 CSS transition 彈回，若 canvas 也複製這段 transition，一旦它的結尾沒有套用（合成層上的 transition 被打斷），canvas 會停在放手時的位移，成為不會彈回的第二張封面（只在 overlay 顯示時，也就是封面縮放過或已重畫高解析時出現）。因此放手的同一次寫入就清除 canvas 的回饋並隱藏它（stage 自己的圖顯示彈回），彈回結束後才重畫；重畫與隱藏都不保留任何回饋屬性。圖層屬性規則不變（只動 opacity 與 canvas 自己的 inline 樣式）。

補記（重影）：放手後 swipe-dismiss 的計時器在彈回動畫的最後幾幀前就清掉 transition 字串，清掉字串並不會停止仍在跑的 CSS transition；若以字串判斷「已靜止」，重畫會用還在位移的 stage 矩形釘住 canvas 並顯示，彈回結束後 canvas 停在舊位置，形成 0.15–0.3 秒的第二張封面。因此靜止判斷改看仍在跑的 feedback transition 與計算後的 translate／scale，canvas 顯示前由當下靜止的矩形重新釘住（opacity 為最後一個寫入），畫完再比對一次，不一致就隱藏重畫（上限 3 次）。測試 `tests/cover-zoom.test.mjs`（重影迴歸：模擬拖曳、放手、彈回、靜止重畫，兩個方向、縮小與放大）。
