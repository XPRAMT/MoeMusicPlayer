# Android Media3 service and Rust-owned playback queue

Android playback uses one Media3 `MediaSessionService`/`ExoPlayer` item while a process-lifetime Rust actor remains the sole owner of queue traversal, session checkpoints, and listening statistics. A bounded JNI command/event bridge carries Play/Pause/Seek and Rust-authorized Next/Previous/Ended decisions plus playback samples; the service generation lets Rust distinguish an attached player from a recreated one and restore the current entry without autoplay. This avoids losing queue work when the Tauri Activity/WebView is destroyed, which makes JavaScript timers and Activity-bound plugin polling unsuitable, and avoids putting a potentially 100,000-track queue in Media3 or creating a second native queue that could advance twice.

Content URIs are transient load inputs and are not session identity. The bridge uses bounded command/event queues, correlated acknowledgements with deadlines, and bounded temporary content leases; notification artwork is a bounded thumbnail while the app artwork path keeps original encoded bytes. A real Android device is still required to verify service lifecycle, notification/controller artwork delivery, audio focus, headset removal, SAF grants, and codec behavior.

Decoder choice: the renderers factory keeps `MediaCodecSelector.DEFAULT` and enables `setEnableDecoderFallback(true)`, so a `MediaCodec` that fails to initialise falls through to the next one the device offers. FLAC, DSD and WavPack do not reach `MediaCodec` at all: Rust decodes them and serves Media3 a float WAV stream (ADR 0016, 0025, 0043). FLAC moved there because on a Sony Xperia G8142 (Android 9) the only FLAC decoder exposed, `OMX.qti.audio.decoder.flac`, fails every 24-bit file after initialising (ADR 0043), which neither decoder ordering nor fallback can repair.
